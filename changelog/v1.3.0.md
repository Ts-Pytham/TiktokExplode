# v1.3.0 — unreleased

Theme: **stop guessing why a request failed.** The library had one bucket for every error
(`TiktokException`) and retried all of them equally, which meant a deleted video cost four
network round-trips and ~12 s before failing, while a genuine soft block was indistinguishable
from a structural change. This release makes the failure mode part of the type system.

---

## Breaking

### Retries are now classified, not blanket

`TiktokClient.GetVideoAsync` used to catch `TiktokException` — the base type — which meant
`TiktokParsingException` and `VideoNotFoundException` were retried too. Both are terminal:
retrying produces the identical result.

The retry predicate is now `TiktokException.IsTransient`.

Observable consequences:

- A removed/private video now throws `VideoNotFoundException` on the **first** attempt.
- A page-structure change now throws `TiktokParsingException` on the **first** attempt.
- Anyone relying on `catch (TiktokException)` being retried loses that behavior. That behavior
  was a bug, not a feature.

### `TikTokBrowser` no longer reports HTTP failures as parsing failures

A non-OK navigation (`response.Ok == false`) used to throw `TiktokParsingException`. It now
throws `TiktokHttpException`. Nothing was being parsed, so the old type was simply wrong — and
it made a 404 look like "TikTok changed their HTML", which is the single most alarming failure
this library can report.

### `VideoNotFoundException` now derives from `MediaNotFoundException`

`catch (VideoNotFoundException)` keeps working. The new base exists so that photo carousels —
landing in a later version via `GetMediaAsync` — have a not-found exception that isn't named
after videos.

### Value objects converted to `record`

`MediaMusic`, `CarouselPost` and `CarouselImage` were `sealed class`; they are now
`sealed record`, matching the convention every other value object already followed.

The original rationale for `class` was micro-optimization. It doesn't hold up: records and
classes have identical memory layout and allocation cost, and the generated `Equals` /
`GetHashCode` / `ToString` / `<Clone>$` members cost IL size, not runtime cycles — and only if
you call them. What we gave up in exchange was convention consistency and `with` expressions.

Caveat we accepted knowingly: structural equality on these types includes signed, expiring CDN
URLs (`MediaMusic.PlayUrl`) and reference-compared `IReadOnlyList<T>` collections
(`CarouselPost.Images`, `CarouselImage.Urls`). Two instances describing the same content fetched
at different times will not compare equal. This is documented on each type. Rejected
alternatives: keeping them as classes (inconsistent, and `MediaCover`/`VideoDownloadLinks` were
already records with the same problem), and overriding equality to compare only `Id`
(semantically correct, but ongoing maintenance for a use case nobody has asked for).

## Added

### `TiktokException.IsTransient`

`virtual bool`, `false` by default. Indicates whether the same request is expected to succeed on
a later attempt.

Chosen over a marker interface (`ITransientTiktokException`) because it adds no public type, and
over an internal-only classification because consumers benefit from it directly: they can build
their own retry policy without knowing our exception hierarchy.

### `TiktokUnavailablePageException` (transient)

Replaces the `TiktokException("TikTok logo detected.")` throw in `HttpFetcher` — a message that
was meaningless to anyone who hadn't read the source.

Covers three previously distinct-but-identically-reported situations, all of which mean _TikTok
declined to answer_ rather than _the content is gone_:

- `HttpFetcher` receives a page without `__UNIVERSAL_DATA_FOR_REHYDRATION__` (the branded shell).
- The hydration payload reports success but carries no `itemInfo` / `itemStruct`.
- The search API responds without a `data` array, or its response is never intercepted.

### `TiktokHttpException` (transient depending on status)

Carries `int StatusCode`. `IsTransient` is `true` for `0` (dropped connection), `408`, `425`,
`429` and `5xx`; everything else is terminal.

`int` rather than `System.Net.HttpStatusCode` because the domain project is BCL-only by rule and
explicitly excludes `System.Net`.

### `MediaNotFoundException` with `TiktokStatusCode`

Surfaces TikTok's own reason code (the `102xx` family) instead of forcing callers to guess from a
message string.

### `TiktokParsingException.Path`

Names the selector or JSON node that could not be resolved, e.g.
`__DEFAULT_SCOPE__.webapp.video-detail`. When TikTok changes its DOM, this is the difference
between a one-evening fix and a bisect through the parser.

Deliberately no `Snapshot` property (a truncated dump of the offending HTML/JSON) yet — worth
doing, but it needs an opt-in switch in `TiktokOptions` and a decision about redaction. Deferred.

### `TiktokOptions.UseRetryJitter` (default `true`)

Randomizes each retry delay by ±25%. The previous delay was fully deterministic, so N concurrent
clients hitting the same block retried in lockstep — which is the most efficient way to convert a
soft block into a hard one.

### `TiktokRetryPolicy` (internal)

`TiktokClient` and `PlaywrightSearchFetcher` had three separate copies of the retry loop, and
they had already drifted: `FetchNextPageWithRetryAsync` caught only `TiktokWafException` while
the other two caught the base type. One implementation now, so classification can't drift again.

Side effect: the `throw new UnreachableException()` sentinel is gone. The loop no longer has an
exit path that isn't a return or a rethrow, so it isn't needed.

### Argument validation

`GetVideoAsync(url)` and `SearchAsync(keyword)` now call `ArgumentException.ThrowIfNullOrWhiteSpace`.
`TiktokOptions.MaxRetries` and `RetryBaseDelay` reject negative values at the setter.

### Integration test for short links

`vm.tiktok.com` / `vt.tiktok.com` were already resolving correctly — but by accident, via the
`AllowAutoRedirect` default on `SocketsHttpHandler` and Playwright's navigation behavior, not by
an explicit decision anywhere in our code. The test pins the behavior so that a future handler
tweak fails loudly instead of silently breaking the most common way people share TikTok links.

## Fixed

### `HttpFetcher` never checked the HTTP status code

`FetchPageAsync` read the response body without ever looking at `IsSuccessStatusCode`. A 403 or
429 fell through to the content checks and surfaced as "TikTok logo detected" — a soft block,
transient — so a hard rate-limit got retried under a misleading exception. Now throws
`TiktokHttpException` before reading the body.

### Deleted videos were indistinguishable from soft blocks

`ExtractItemStruct` threw `VideoNotFoundException` whenever `itemStruct` was missing. That node
is also absent when TikTok soft-blocks the request and returns an empty hydration payload — two
opposite situations, one exception.

The parser now reads `__DEFAULT_SCOPE__.webapp.video-detail.statusCode`, which TikTok populates
itself: `0` means the item exists, non-zero identifies why it doesn't. Missing `itemStruct` with
`statusCode == 0` is a soft block (`TiktokUnavailablePageException`, retried); non-zero is
`VideoNotFoundException` (terminal, with the code attached).

This replaces inference with TikTok's own answer.

### Cover `HttpClient` had no connection lifetime

`DownloadClientExtensions` used a static `new HttpClient()` with the default handler, so pooled
connections never recycled and DNS went stale in long-lived processes (the bot). Now backed by a
`SocketsHttpHandler` with a 10-minute `PooledConnectionLifetime`.

Not changed: covers still bypass `TiktokDownloadClient`. Cover URLs are pre-signed and need
neither cookies nor TikTok headers, so routing them through the session client would buy nothing.

### Cover downloads buffered the whole response in memory

`GetAsync` defaults to `ResponseContentRead`. Switched to `ResponseHeadersRead` and streamed
straight to disk — relevant for multi-MB animated WebP covers under concurrency.

### Cover downloads threw the base `TiktokException`

Now `TiktokHttpException` with the status attached, consistent with the rest of the library.

## Deprecated

Both removed in 2.0.

| Deprecated                             | Replacement                  | Why                                                                                       |
| -------------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------- |
| `TiktokOptions.MaxWafRetries`          | `MaxRetries`                 | Retries are no longer WAF-specific                                                        |
| `DownloadImageAsync(video, …)`         | `DownloadCoverAsync`         | It downloads the cover, not a post image — confusing next to the `CarouselImage` overload |
| `DownloadAnimatedImageAsync(video, …)` | `DownloadAnimatedCoverAsync` | Same, and the README already documented the new name                                      |

Both forward to the new members, so nothing breaks at runtime.

## Deferred

Discussed for this release and consciously postponed:

- **`GetMediaAsync` → `Video` | `Carousel`.** The API's biggest gap: carousels are a first-class
  entity, `SearchAsync` returns them, `DownloadImageAsync` handles their images — but there is no
  way to _request_ one by URL. Blocked on deciding whether it goes on a new `IMediaClient` (which
  `IVideoClient` would extend) or on `IVideoClient` directly, and on unifying the three places
  that currently parse `Media` fields. Note for whoever picks this up: do **not** discriminate by
  URL path — TikTok serves carousels under both `/photo/` and `/video/`. Use the presence of
  `itemStruct.imagePost`.
- **Shared `TiktokDownloadClient` between `TiktokClient` and `TiktokSearchClient`.** Each
  instantiates its own with `new()`, so an app using both keeps two independent `CookieContainer`s
  and two socket pools — the search session's cookies never reach the download path. The two
  clients stay separate (different fetchers, different use cases); only the download client should
  be shareable, and it needs explicit ownership tracking so the first `DisposeAsync` doesn't kill
  the other client's HTTP stack.
- **`ILogger` in Infrastructure.** Postponed on purpose: the exception context added in this
  release (`IsTransient`, `StatusCode`, `TiktokStatusCode`, `Path`) covers most of "why did it
  fail?" with zero dependencies. Revisit only once that proves insufficient. If we do it:
  `Microsoft.Extensions.Logging.Abstractions` with an optional `ILogger<T>` defaulting to
  `NullLogger`, not `EventSource` — nobody is going to run `dotnet-trace` against a scraping library.
- **`TiktokParsingException.Snapshot`.** See above.
- **Packaging hygiene** — SourceLink, symbol packages, deterministic/CI builds, package
  validation against 1.2.2. Purely additive `.csproj` work, no code impact.
- **Search pagination.** Still blocked on identifying the real scroll container and the
  `IntersectionObserver` sentinel with `Headless = false`. One approach not yet tried: don't
  simulate scrolling at all — locate the observed sentinel element and call
  `ScrollIntoViewIfNeededAsync()` on it, which lets Playwright move whichever container actually
  owns the scroll.
